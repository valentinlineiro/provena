# ADR-001 — Architectural Reconciliation for v0.7.0

## Status
**Accepted** (2026-08-07)

## Context & Motivation
Provena has evolved rapidly from a canonical professional identity engine to a continuous market observer with a shared market architecture (O2) and an attention-filtering inbox.

However, the codebase, documentation (`README.md`, `docs/architecture.md`), product roadmap (`docs/roadmap.md`), and version tags have diverged. `package.json` files remain at `0.1.0` while git releases reach `v0.6.0`, and recent advances in continuous market sync are unreflected in the high-level architecture docs.

To establish governance and maturity before releasing `v0.7.0`, we perform an **Architectural Reconciliation**: aligning software, documentation, versioning, roadmap, and research program so they describe the exact same operational system.

## Decision
We reconcile Provena's software architecture, documentation, roadmap, versioning hierarchy, and research program prior to releasing `v0.7.0`.

1. **Architecture Freeze Record**: Establish `docs/architecture/freeze-v0.7.0.md` as the authoritative record of stable, experimental, and unstarted components for `v0.7.0`.
2. **Separation of Software and Research**: Explicitly distinguish between the monorepo software release (`v0.7.0`) and the scientific research program (`Protocol v1`, `K12`, `Attention Validation`). Research artifacts live under `docs/research/` and `experiments/`.
3. **Operational Knowledge Versioning Rule**: Define `Operational Knowledge Version` as representing promoted production knowledge used by the decision engine. Experimental knowledge (such as `K12-GTM-002`) does NOT change this version until formally promoted. Operational Knowledge Version remains `0` until a promotion occurs.
4. **Structured 7-Step Execution Order**: Execute reconciliation in strict sequence:
   - Step 1: Architecture Freeze Record
   - Step 2: Fix Technical Debt & Bugs
   - Step 3: Reconcile Documentation
   - Step 4: Reconcile Versioning
   - Step 5: Release Audit (Functional, Architectural, Product)
   - Step 6: Tag `v0.7.0`
   - Step 7: Release Retrospective

## Out of Scope
The following activities are strictly out of scope for the `v0.7.0` architectural reconciliation:
- New K12 experiments or GTM splits
- Attention Validation implementation
- UX redesign or layout overhauls
- New market data sources or scraper integrations
- New features or domain model additions

## Architectural Classification (`docs/architecture/freeze-v0.7.0.md`)

### Stable (Operational Production)
- **Identity Model**: Aggregate root Profile, YAML loaders, referential integrity checks.
- **Decision Protocol (Protocol v1)**: Deterministic evaluation `evaluateOpportunity(jd, profile)` (APPLY/CONSIDER/SKIP), semantic trace from claims to canonical capabilities.
- **Shared Market Architecture (O2)**: Market posting ingestion (Greenhouse), deduplication, Neon PostgreSQL storage + Cloudflare Cron sync.
- **Attention Inbox**: Market opportunity inbox, filtering by candidate preferences and ordering by relevance.
- **Continuous Synchronization**: Automated pipeline (Worker + Cron + PostgreSQL + KV snapshot).

### Experimental (Research & Active Experiments)
- **K12 (Market Knowledge Acquisition)**: Market requirement pattern extraction (`MarketPatternDefinitions`), GTM splits (K12-GTM-001/002), empirical learning reports.

### Not Started / Vision (Future Program)
- **Attention Validation**: Empirical measurement of attention reduction.
- **Outcome Learning**: Application outcome feedback loop.

## Versioning Hierarchy Rules

1. **Software Monorepo Version (`v0.7.0`)**:
   - Sincronized across root `package.json` and all `packages/*/package.json`.
   - Identifies the version of the executable software, web UI, CLI, worker, and database schemas.
2. **Decision Protocol Version (`Protocol v1`)**:
   - Identifies the evaluation contract, invariants, and `OpportunityEvaluation` schema.
3. **Operational Knowledge Version (`0`)**:
   - Represents the promoted operational knowledge consumed by the decision engine in production.
   - Experiments do NOT increment this version. It advances only when knowledge is officially promoted to production.

## 7-Step Execution Sequence

```
1. Architecture Freeze Record  (docs/architecture/freeze-v0.7.0.md)
              ↓
2. Fix Technical Debt & Bugs   (UI flakiness, DB fallbacks, bundle isolation)
              ↓
3. Reconcile Documentation     (README, PROJECT_MEMORY, ARCHITECTURE, ROADMAP, CHANGELOG)
              ↓
4. Reconcile Versioning        (Monorepo package.json sync to 0.7.0)
              ↓
5. Release Audit               (Functional, Architectural, Product audit)
              ↓
6. Tag v0.7.0                  (Git tag & release notes)
              ↓
7. Release Retrospective       (docs/releases/v0.7.0-retrospective.md)
```

## Release Audit Checklist (Step 5)

### Functional
- [ ] `npm run typecheck` passes with zero errors across the monorepo.
- [ ] `npm test` passes 100% of test suites cleanly.
- [ ] Graceful fallback when Neon PostgreSQL is unconfigured or offline in development.
- [ ] Cloudflare Worker build excludes test runner artifacts.

### Architectural
- [ ] `docs/architecture/freeze-v0.7.0.md` created and accurate.
- [ ] `PROJECT_MEMORY.md` created/updated reflecting the transition to continuous market observer (O2) and attention system.
- [ ] `docs/roadmap.md` updated with the 6-phase continuum (P1 Canonical Identity → P6 Helping to Look Less).
- [ ] `docs/architecture.md` updated with the complete pipeline (`Identity → Decision → Market → Attention`).
- [ ] Monorepo `package.json` files synchronized to `"version": "0.7.0"`.

### Product
- [ ] `README.md` updated with revised thesis, system status table, and clean QuickStart.
- [ ] `CHANGELOG.md` updated with `v0.7.0` release entry.
- [ ] `docs/releases/v0.7.0.md` created with full release notes.
- [ ] QuickStart verified via clean execution test.
- [ ] Every experimental component clearly labelled as `Experimental`.

## Post-Release Activity (Step 7)
Immediately following `v0.7.0` tagging, write `docs/releases/v0.7.0-retrospective.md` answering:
1. What went well during this reconciliation?
2. What technical/architectural debt remains?
3. What is the next operational frontier?
